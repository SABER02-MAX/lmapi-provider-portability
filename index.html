能跑 ≠ 语义相同It Runs ≠ It Means the Same

同一段「OpenAI SDK 风格」的代码，把 base_url 换成 Claude、Gemini 或 vLLM 兼容端点——HTTP 200 只说明端点存在，参数名、默认值、流式结构、token 计费都可能悄悄不同。这个页面用交互方式拆给你看。Take the same "OpenAI-SDK-style" code and point base_url at Claude, Gemini, or a vLLM-compatible endpoint — an HTTP 200 only means the endpoint exists. Parameter names, defaults, streaming shapes, and token billing can all quietly differ. This page breaks it down interactively.

01 · 问题01 · The Problem

「OpenAI 兼容」是一种幻觉"OpenAI-Compatible" Is an Illusion

「兼容层」只承诺请求格式长得像，不承诺语义相同。同一段代码换端点后，失败会以三种面貌出现：A "compatibility layer" only promises the request shape looks similar — not that the semantics are identical. After switching endpoints, the same code fails in three ways:

直接报错（响亮）Hard error (loud)

目标 API 不存在的参数/字段，被严格校验的端点拒绝：Claude 缺 max_tokens 会 400，传未知参数会被拒；vLLM 模型没有 chat template 时 chat 请求直接报错。Strict endpoints reject parameters or fields they don't have: Claude returns 400 without max_tokens; vLLM chat requests fail outright when the model has no chat template.

400 invalid_request_error · BadRequestError

静默忽略（最危险）Silently ignored (most dangerous)

兼容层把不认识的参数悄悄丢掉，HTTP 200 照常返回：Gemini 兼容层会静默忽略白名单之外的参数；frequency_penalty、seed 在许多端点被无视。你以为在控温度，其实根本没生效。Compatibility layers quietly drop unknown parameters and still return 200: Gemini's compat layer silently ignores params outside its whitelist; frequency_penalty and seed are ignored by many endpoints. You think you're controlling sampling — you aren't.

200 OK · parameters dropped

语义漂移（最难查）Semantic drift (hardest to debug)

参数都存在、都能跑，但含义不同：max_tokens 在不同端点 = 输出上限 / 必填项 / 映射到 max_output_tokens；同一个 chat template 渲染出的 token 不同；temperature 默认值与实现不同。Parameters exist and run, but mean different things: max_tokens becomes a required field, or maps to max_output_tokens; the same chat template renders different tokens; temperature defaults differ.

200 OK · same call, different output

OpenAI基准代码（参考实现）Baseline (reference implementation)
from openai import OpenAI
client = OpenAI()

resp = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": "你是简洁的助手，只输出 JSON。"},
        {"role": "user",   "content": "把这句话里的城市抽出来：北京是中国首都。"},
    ],
    max_tokens=200,            # 输出上限（可省略）
    temperature=0.7,           # 采样温度
    response_format={"type": "json_object"},  # JSON 模式
    frequency_penalty=0.5,      # 频率惩罚
    seed=42,                  # 随机种子（尽力而为）
)
print(resp.choices[0].message.content)  # 响应结构
差异清单：这是对照基准Verdicts: this is the baseline
  • 基准BASE所有对比以这段代码为起点。它本身也有自己的坑：推理模型（o 系列 / gpt-5）上 OpenAI 官方更推荐 max_completion_tokens，且 seed 是「尽力而为」而非保证。All comparisons start from this snippet. Even it has caveats: on reasoning models (o-series / gpt-5) OpenAI recommends max_completion_tokens, and seed is best-effort, not guaranteed.
  • 注意NOTEmessages 是 OpenAI 的核心结构：system 是 messages[0] 的一个角色；usage.prompt_tokens / completion_tokens 是计费字段。这两点在其他端点都不是这样的。

04 · 交互 · 陷阱测试04 · Interactive · Pitfall Quiz

这些坑，你能全对吗？Can You Get All of These Right?

每题选一个答案，点完即见解析与官方出处。Pick an answer per question; the explanation and official source appear instantly.

Q1

用 Claude 原生 API，请求体里不传 max_tokens，会发生什么？Calling the Claude native API without max_tokens in the body — what happens?

对。max_tokens 在 Anthropic Messages API 中是 required 字段，且不同模型有不同上限。OpenAI 的惯例是「可省略、有默认」，搬代码时最容易漏的就是这种「对方强制要求」的参数。Correct. max_tokens is a required field in the Anthropic Messages API, with per-model caps. OpenAI's convention is "optional with a default" — required-on-the-other-side params are the easiest to miss when porting.
出处：Source: docs.anthropic.com/en/api/messages
Q2

把 OpenAI 的 response_format={"type":"json_object"} 原样发给 Claude 原生 API？Sending OpenAI's response_format={"type":"json_object"} verbatim to the Claude native API?

对。Anthropic 是「严格型」：未知参数会被拒绝。想要稳定 JSON 输出，得改用 system 提示 + 工具调用（input_schema）或预填充——接口完全不同，不是「加个参数」的事。Correct. Anthropic is "strict": unknown parameters are rejected. For reliable JSON you must switch to system hints + tool use (input_schema) or prefill — a different interface, not "one more parameter".
出处：Source: docs.anthropic.com/en/api/messages
Q3

通过 HTTP 直发，把 frequency_penalty=0.5 交给 Claude，结果？Sending frequency_penalty=0.5 to Claude via raw HTTP?

对。Claude 没有 penalty 类参数（连 presence_penalty、seed 都没有）。这与 vLLM / Gemini 兼容层的「静默忽略」正好相反——同一段代码，一个端点拒绝、一个端点假装没看见，调试难度完全不同。Correct. Claude has no penalty parameters (nor presence_penalty or seed). This is the opposite of the "silent ignore" behavior of vLLM / Gemini compat — one endpoint rejects, another pretends not to see it.
出处：Source: docs.anthropic.com/en/api/messages
Q4

给 Gemini 3.6+ 原生 API 传 temperature=1.5？Passing temperature=1.5 to the Gemini 3.6+ native API?

对。官方文档明确：Gemini 3.6+/4 会忽略自定义 temperature / top_p / top_k 并返回弃用警告头——响应是 200，但你的采样参数从未生效。这是「静默忽略」的教科书案例。Correct. Official docs state Gemini 3.6+/4 ignore custom temperature/top_p/top_k and return deprecation warning headers — 200 OK, but your sampling params never applied. Textbook "silent ignore".
出处：Source: ai.google.dev/gemini-api/docs/text-generation
Q5

用 OpenAI SDK + base_url 指向 Gemini 兼容层，请求返回 200——能证明行为与 OpenAI 等价吗？OpenAI SDK with base_url pointed at Gemini's compat layer returns 200 — does that prove behavioral equivalence?

对。这是「能跑 ≠ 语义相同」的核心。兼容层官方文档明示：白名单之外的参数会被静默忽略；reasoning_effort 等只做近似映射。验证迁移是否成功，必须用 eval 对比行为，而不是看 HTTP 状态码。Correct — the heart of "it runs ≠ it means the same". The compat docs state params outside the whitelist are silently ignored; reasoning_effort is only approximately mapped. Validate a port by comparing behavior with evals, not by checking the HTTP status.
出处：Source: ai.google.dev/gemini-api/docs/openai
Q6

在 vLLM 上把同一段 messages 换给另一个模型（不同 chat template）？On vLLM, feeding the same messages to another model with a different chat template?

对。vLLM 依赖模型 tokenizer 自带的 Jinja2 chat template；模型没有模板时 chat 请求直接报错。即使都有模板，不同模板会把 system / user 包进不同的 control tokens——这是子任务 A（Chat Template）的主题，也是「同一段代码换模型 = 不同输入」的最直观例子。Correct. vLLM requires a Jinja2 chat template in the model's tokenizer — chat requests error if it's missing. Even with templates, different templates wrap system/user in different control tokens — the topic of Subtask A, and the clearest case of "same code, different input".
出处：Source: docs.vllm.ai · OpenAI-Compatible Server

06 · 结论06 · Takeaways

三句话带走Three Sentences to Take Away

① 兼容层承诺的是「信封」① Compat promises the "envelope"

「OpenAI 兼容」只覆盖请求格式。模型行为、默认值、采样、计费都是各家自己的——200 只证明端点存在。"OpenAI-compatible" covers only request shape. Behavior, defaults, sampling, and billing stay vendor-specific — 200 proves the endpoint exists, nothing more.

② 失败有三种形态② Failures come in three forms

报错（Claude 拒未知参数）好查；静默忽略（Gemini 兼容层、vLLM）最危险；语义漂移（同名参数不同含义）最难 debug。先判断你的端点属于哪种性格。Hard errors (Claude rejecting unknowns) are easy; silent ignores (Gemini compat, vLLM) are dangerous; semantic drift (same name, different meaning) is the hardest to debug. Know your endpoint's personality first.
